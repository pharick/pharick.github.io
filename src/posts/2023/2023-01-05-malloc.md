I wrote a dynamic memory allocator in C for the École 42 malloc project and
packaged it as libft_malloc.so, a shared library that replaces the system
malloc, free and realloc when injected with DYLD_INSERT_LIBRARIES (the run.sh
script does this on macOS).

Memory comes from mmap in three zone classes. A TINY heap is four pages and
serves blocks up to 1/128 of that; a SMALL heap is sixteen pages with the same
ratio; anything larger gets its own LARGE mapping rounded up to a multiple of
the SMALL heap size. Each heap therefore holds at least a hundred blocks of its
class, which is what amortises the cost of a system call. Inside a heap, blocks
form a doubly linked list of 32-byte headers followed by data; request sizes are
rounded to 16 and the heap header is 48 bytes, so every returned pointer is
16-byte aligned.

The interesting logic is in block reuse. malloc first scans freed blocks of the
right class for one large enough to hold the request plus a new header and
splits it; free marks a block, merges it with free neighbours in both
directions, and when the last block of a heap goes away the heap is unmapped,
except that one TINY and one SMALL heap are always kept so the next small
allocation does not pay for a new mapping. Before mapping, the size is checked
against RLIMIT_DATA.

All entry points take a single pthread mutex and call unlocked _impl functions,
which is how realloc reuses malloc_impl and free_impl without deadlocking.
show_alloc_mem prints heaps in allocation order with per-block address ranges
and a total; show_alloc_mem_ex adds a hex dump.

The repository carries the subject's six test programs but no automated harness.
Known weak spots: the remainder size after splitting is computed with t_block
pointer arithmetic and comes out too small, realloc always moves the block, and
pointer validation walks every block.
